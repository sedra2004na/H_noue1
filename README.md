# 🏥 نظام إدارة المشافي والمراكز الطبية التخصصية المتكامل
### Al-Rahma Hospital & Medical Center Management System (Enterprise HMS)
> **مشروع تخرج هندسي متكامل النواحي الهندسية، الإكلينيكية، التشغيلية، والأمنية**

---

## 📌 1. نظرة عامة على المشروع (Executive Summary)
منظومة رقمية سحابية متقدمة لإدارة المشافي والمراكز الطبية التخصصية، مبنية وفق أعلى المعايير الهندسية للأمان والخصوصية الطبية (**HIPAA Compliance** & **ISO-27001**).
تغطي المنظومة كافة دورات العمل السريرية (Clinical Workflows) والإدارية، بدءاً من تسجيل المريض في مكتب الاستقبال ومطابقة هويته، مروراً بالكشوفات السريرية، جدولة العيادات، الفحوصات المخبرية، تسكين أجنحة العناية المركزة (ICU Beds)، وحتى إصدار الفواتير والتنبيه التلقائي للتداخلات الدوائية والحساسية.

## 🏗️ 2. الهيكلية المعمارية والتقنيات (Architecture & Tech Stack)

| الطبقة (Layer) | التقنية المستخدمة | الدور الهندسي |
| :--- | :--- | :--- |
| **الواجهة الأمامية (Frontend)** | React 19 + TypeScript + Vite | واجهات تفاعلية فائقة السرعة، بنية Modular، ومظهر مظلم دائم (Permanent Dark Mode) |
| **التصميم والأسلوب (Styling)** | Tailwind CSS + Lucide Icons | واجهات طبية حديثة، خطوط عربية واضحة، وتوافق تام مع الهواتف والحواسيب |
| **الخادم الموثوق (Backend)** | Node.js + Express (مع توافقية معمارية NestJS) | معالجة الطلبات، تطبيق حماية مسارات الـ API، والـ Middleware الأمني |
| **قواعد البيانات (Database)** | PostgreSQL (Cloud SQL) + Prisma + Drizzle ORM | قاعدة بيانات علائقية كاملة الجداول، مع تخزين ملفي محلي دائم (`data/hospital_db.json`) للمزامنة |
| **المخطط ونمذجة البيانات (ORM)** | Prisma Schema 11 Models | مخطط علائقي متكامل يشمل المرضى، الأطباء، المواعيد، التحاليل التاريخية، الأسرة، والفواتير |
| **التزامن اللحظي (Real-time)** | Server-Sent Events (SSE) + Fast Polling | بث فوري لكافة التعديلات السريرية عبر جميع أجهزة الطاقم دون الحاجة لتحديث الصفحة |
| **التحقق وتفادي الأخطاء** | Zod Schema Validation | فحص الـ DTOs ومنع هجمات الحقن (SQLi & XSS) |
| **الأمان وسجل التدقيق** | SHA-256 + Salts, Strict RBAC, IDOR Guards | حماية مسارات السيرفر، وسجل تدقيق غير قابل للإنكار (Non-Repudiation Audit Log) |
| **التوثيق وتوصيف الـ API** | OpenAPI / Swagger Structure | وثائق الـ Endpoints القياسية بصيغة JSON المعيارية |

## 🔐 3. المعايير الهندسية والأمنية المطبقة (Engineering & Security Standards)

### أ. الفصل الصارم للصلاحيات (Strict Role-Based Access Control - RBAC)
- **الفحص على مستوى الخادم (Server-Side Enforced)**: لا يتم الاعتماد على إخفاء الأزرار في الواجهة فقط، بل تفحص كل دالة في الـ Express عبر `enforceRole` ترويسة الطلب؛ ومحاولة دخول غير مصرح بها تُرجع مباشرة رمز الحظر `403 Forbidden`.
- **أربعة أدوار منفصلة في النظام**:
  1. `admin` (مدير النظام): كامل الصلاحيات وإدارة الأطباء والكادر.
  2. `doctor` (الطبيب المعالج): البوابة السريرية، التحاليل الحرجة، والوصفات الطبية.
  3. `staff` (موظف الاستقبال): تسجيل المرضى، حجز المواعيد، الفواتير، وتسكين الأسرّة.
  4. `patient` (بوابة المريض): الوصول الذاتي المقيد لملفه الشخصي فقط ومواعيده.

### ب. حماية معرفات الوصول المباشر (Anti-IDOR Protection)
- يُمنع المريض أو أي طرف غير مخول من استعراض ملفات مرضى آخرين بمجرد تغيير الرقم في الطلب (`/api/patients/:id`). يتم فحص الهوية وتسجيل أي محاولة وصول مشبوهة كحدث حظر `IDOR_ACCESS_BLOCKED` في سجل التدقيق.

### ج. محرك التنبيه للتداخلات الدوائية والحساسية (Drug & Allergy Safety Engine)
- فحص فوري ومباشر لاسم الدواء مقابل حساسيات المريض المسجلة في ملفه (مع التعرف الذكي على الحساسيات المتصالبة مثل البنسلين والأوجمنتين).
- كشف التداخلات الدوائية الخطرة (مثل الوارفارين والمسكنات، أو الأنسولين وحاصرات بيتا) وتنبيه الطبيب فورياً.

### د. جدار الحماية ضد الأخطاء المفاجئة (Global Error Boundary)
- تغليف النظام بـ `Global Error Boundary` يمنع الشاشة البيضاء (`White Screen of Death`)، مع معالج أخطاء مركزي في السيرفر يعيد استجابات موحدة بصيغة JSON.

### هـ. منع هجمات التخمين والتعارض (Rate Limiting & Concurrency Control)
- **Rate Limiting**: حظر محاولات التخمين لكلمات المرور عند تجاوز 5 محاولات خاطئة خلال 15 دقيقة.
- **Concurrency Locks**: منع حجز نفس موعد الطبيب في ذات الدقيقة لمريضين مختلفين (`409 Conflict`).

## 🚀 5. خطوات التثبيت والتشغيل محلياً (Local Setup & Run)

### المتطلبات الأساسية:
- **Node.js** (الإصدار 18 أو أحدث)
- **npm** أو **bun**

### الخطوات:
```bash
# 1. استنساخ المستودع (Clone)
git clone <repository-url>
cd hospital-management-system

# 2. تثبيت الحزم والمكتبات
npm install

# 3. إعداد متغيرات البيئة (.env)
cp .env.example .env

# 4. تشغيل خادم التطوير المدمج (Express + Vite)
npm run dev
```

التطبيق سيعمل مباشرة على: `http://localhost:3000`

## 🎓 7. أسئلة متوقعة من لجنة المناقشة وإجاباتها النموذجية

1. **س: كيف تضمنون عدم تضارب حجز سرير أو موعد لمريضين بنفس اللحظة؟**
   - **ج:** نطبق فحص Concurrency Check في السيرفر وقاعدة البيانات؛ عند محاولة الحجز في نفس الوقت يرفض الطلب الثاني بكود `409 Conflict` مع إشعار الموظف فورياً.

2. **س: ماذا يحدث لو انقطع الاتصال أو أغلقت الصفحة أثناء كتابة الطبيب للتقرير؟**
   - **ج:** المنظومة مزودة بـ `Global Error Boundary` لمنع انهيار الواجهة، بالإضافة إلى الحفظ التلقائي المؤقت بالـ LocalStorage وتزامن خلفي فوري مع السيرفر عبر `SSE`.

3. **س: كيف تمنعون التلاعب بسجلات المرضى الطبية السابقة؟**
   - **ج:** نعتمد على سياسة **الحذف الناعم (Soft Delete)** مع حقول `is_deleted` و `deleted_at`، وسجل تدقيق أمني مفصل `audit_logs` يسجل هوية الطبيب، التوقيت بدقة، ونوع الإجراء بصيغة غير قابلة للتعديل أو الإنكار (**Non-Repudiation**).
